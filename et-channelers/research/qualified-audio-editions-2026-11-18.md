# Qualified YouTube audio editions

A public recording may offer an audio-only file with uncertain original-track labels, or a combined MP4 that requires audio extraction. The collection dashboard accounts for both as qualified audio editions, with explicit uncertainty about the original track and spoken language. This capability reads saved metadata only. It starts no downloader, browser, Drive operation, transcription or media verification job. An empty qualified-edition journal contributes zero; supporting a receipt type does not establish that any real file has passed it.

The private acquisition worker must first obtain one complete selected format-18 response, extract its AAC stream without re-encoding, and preserve the ordered packet payloads, codec configuration, padding and timing. The recorded quality result must bind the exact source and derived file hashes and the existing verifier artifact. Whole-response Content-Length or full-extent 206, received/written byte counts, no redirect/retry and the observed body hash must agree. The archive contains `audio-extract.m4a` and canonical `provenance.json` under the creator's `AudioExtracts/<video>/<source-sha256>/` directory. Both require observed Drive MD5, size and distinct IDs. Local SHA-256 is never described as an observed remote hash.

`qualified_edition_receipts.py` checks that schema, the archived provenance bytes and the actual pair proofs. `ingestion_status.py` joins accepted records to the selected creator, video and tab; an unrelated creator or legacy/partial receipt does not count. Coverage uses one video-ID union, with native audio first, publisher audio second and additional qualified YouTube editions third. The channel CSV adds `qualified_youtube_only_audio`; the video CSV uses `youtube_track_unverified`. Existing dated snapshots that omit the new category continue to render as zero.

These receipts do not establish original-track identity, spoken language, speaker identity, recording/edit equivalence, translation status, full speech coverage or text accuracy. Native audio, native HTTP-success history, captions and ASR counts remain independent. A qualified audio transfer cannot reset a native refusal streak. Future analysis must use each edition's provenance and its own transcript binding rather than silently substituting it for another recording.

Tests use invented metadata and file fingerprints. They cover canonical provenance, detached file proofs, weaker quality claims, partial bodies, remote-pair mismatch, native/publisher overlap, creator joins, legacy rejection and the actual dashboard JavaScript's count, activity and CSV behavior. Actual acquisition and publication still require their separate owned execution and receipts.

## AAC profile preservation

The legacy combined-MP4 receipt remains bound to its AAC-LC verifier. A separate reviewed private component supports AAC-LC and HE-AAC under `progressive_MP4_AAC_LC_HE_AAC_packet_preserving_streamcopy_v1`. Its primary artifact is SHA-256 `5915a2b689de11fed5ea41956f084e55c967c22e6c63b925202e48611ec058a4`, 8,131 bytes; it reuses the immutable 10,864-byte packet-summary component pinned by the legacy reader. Both artifact descriptors must match inside the preservation result and its enclosing qualification. A legacy verifier label cannot validate HE-AAC.

The new receipt branch permits at most 32 MB each for the source and extracted file. It requires identical AAC profile, sample rate, channels and codec extradata; identical ordered packet payload hashes, sizes, counts, padding and timing; matching duration; and the same complete HTTP and paired Drive proofs. Native identity and transcript flags remain unverified. Supporting this metadata contract establishes no actual HE-AAC archive until a real extraction and paired receipt pass it.

## Streaming packet summaries for larger recordings

A third metadata contract binds the separate bounded-memory preservation component, SHA-256 `f903fddac2f02850d409a4511c897d47a04f976cf38a2ca8924b54d0c24a5f60` (18,424 bytes). It consumes ffprobe JSON one packet at a time and preserves the same ordered packet, configuration, padding, timing and duration requirements. The legacy verifier is identified as a digest-compatibility reference, with execution explicitly false.

Only this new artifact permits source and extracted files up to 2 GB each, with a stricter output permit supplied by the caller. Packet count must fit the positive packet payload and actual file bytes; it has no fixed 200,000-packet cutoff. The older artifact branches retain their original limits. These are byte and resource bounds; the receipt reader adds no recording-duration filter. Whole-body HTTP observations, canonical provenance, observed Drive MD5/size/distinct IDs and all identity qualifiers remain required. Supporting this receipt contract establishes no new archive by itself.

## Unchanged audio-only editions

A separate pure reader, `qualified_direct_audio_receipts.py`, validates exact HTTPS format-140 AAC/M4A editions under `AudioEditions/<video>/<source-sha256>/audio.m4a` plus canonical `provenance.json`. The archived audio must have exactly the source file's bytes, MD5 and SHA-256 before and after the existing strict container probe. The selected full response, exact byte count and whole 200/full-extent 206 proof must agree. The existing pinned probe must show one AAC audio stream, zero video streams, positive packets, clean strict extent and a duration matching the selected recording. Original-track/language flags remain unverified. This branch uses the unchanged file and its container proof; the combined-MP4 branch retains its separate AAC packet-preserving remux proof.

Both variants share the bounded qualified-edition journal, creator/video/tab join and deduplicated audio union. A direct audio edition adds zero native, caption or ASR coverage. The new tests cover transport replay, partial extents, altered file/quality/provenance proofs, incorrect remote pairs and overlap with native or combined-video editions. Supporting this receipt type establishes no actual new archive: the current direct-audio worker is separately prepared and requires its own admitted execution and real pair receipts.

## Completed cohort status

After a finite native cohort closes, its latest bound terminal can remain visible with its completed frame/item totals and `process_confirmed=false`. This requires the actual closed owned-job graph, complete child audits, released matching lease/resource row and unchanged scope/code/HTTP bindings. An expired grant does not turn a historical completed observation into a running job. A current STOP or provider circuit still takes precedence. This fixes the dashboard's fallback to an older paused cohort after the newest successful finite pass.
